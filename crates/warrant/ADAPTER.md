# 适配器契约 v0.1（Adapter Contract）

第二份规范。`SPEC.md` 管"什么算发生过"；本文件管**一个被控系统要长成什么样，才有资格参与认定**。

> **归属同 `SPEC.md`（2026-09-29）**：本契约由 ZeroPage 承载，**运行时权威在 ZeroPage**；
> 原 `信使系统` 仓的适配器（如 EDA 桥）降为**蓝本与参照实现**。
> 待落地：ZeroPage 侧的**适配器运行时**（`capability` / `act` / `observe` 三原语 + 三态 + 档位申报）
> —— 见 `kb/信使融合进ZeroPage-现状与路线图-2026-09-29.md` 阶段 F3（用户已定：**后置**）。

> **一条禁令**：本文件与 `SPEC.md` 都不得出现任何具体软件名、API 名、传输细节。一旦出现，规模就从 O(1) 退回 O(N)。

---

## 0. 适配器产出的是什么

不是"成功"，不是"状态"，是**两样东西**：

| 产物 | 归属 | 入账后 |
|---|---|---|
| **声明条目**（`kind = claim`） | 发起动作的一方（通常是 AI） | 状态 `PROPOSED`，等观测 |
| **观测条目**（`kind = observation`） | 验证器 | 作为投影的基元，决定声明的状态 |

**适配器不产生"动作已成功"这种结论。** 它只能给出观测事实；比对与定级由核心按 `SPEC.md` §4 计算。适配器不被信任——它和被控软件一样会撒谎。

---

## 1. 三个原语

### 1.1 `capability`

```json
{"id": 1, "op": "capability"}
```

```json
{"id": 1, "ok": true, "result": {
  "adapter": "名称+版本",
  "types":   ["warrant://types/<domain>.<object>.<verb>@1"],
  "channels": [{"id": "c1", "tier": "C1", "read_only": true, "desc": "新会话重开读回"}],
  "max_tier": "C2",
  "reversible": false,
  "exclusive": true,
  "idempotency": "nonce 语义说明"
}}
```

无副作用；启动即可答；**如实申报**——低报允许，高报致命。做不到第二条通道就申报 `max_tier = C0`。

### 1.2 `act`

```json
{"id": 2, "op": "act", "type": "warrant://types/...", "args": {...}, "nonce": "..."}
```

| 返回值 | 含义 | 之后必须做什么 |
|---|---|---|
| `accepted` | **已受理，不是做成了** | 必须 `observe` |
| `rejected` | 明确拒绝，带 `reason` | 记为 `REJECTED` |
| `unknown` | 无从判断（超时、模态框吞消息、进程异常） | 必须 `observe`，**禁止推断** |

- **声明式**：`args` 描述目标状态，不是点击序列或坐标。
- **幂等**：同一 `(type, args, nonce)` 重放不得产生第二个副作用。
- **协议里不存在"act 成功"这个终态。**

### 1.3 `observe`

```json
{"id": 3, "op": "observe", "subject": "<claim id>", "expect": {...}, "channel": "c1"}
```

```json
{"id": 3, "ok": true, "result": {
  "method": "…",
  "result": {"observed_value": "1000", "unit": "ohm"},
  "observed_at": "2026-09-12T04:00:00Z",
  "tier": "C1",
  "evidence": ["<路径或哈希>"]
}}
```

观测无法完成时（例如进程失联），返回 `reason` 而**不带** `result`——这会产生一条 `unknown` 观测。

- **不返回 verdict。** 比对由核心按 `SPEC.md` §4.1 完成。适配器无权宣布"一致"。
- **必须使用与 `act` 不同的通道。** 同一会话读回最多算 `C0`。
- **只读**：不得改变被控对象，不得抢租约。
- 必须回报**实际**使用的通道与档位。
- 不确定就不给 `result`。**禁止猜测。**

---

## 2. 观测通道档位

| 档 | 定义 | 可否支撑冻结 |
|---|---|---|
| `C0` | 同一会话读回 | 否 |
| `C1` | 新会话 / 新进程重开读回 | 是 |
| `C2` | 离线产物（文件哈希、导出文本），第三方可离线复算 | 是 |
| `C3` | 跨机 / 跨人复核 | 是 |

这条规则是整个契约里价值最高的一条：它把"我改完自己读了一遍"和"我改完、换个进程重新打开文件读了一遍"在协议层面区分开。**前者是幻觉的温床，后者才是认定。**

---

## 3. 线格式

JSON Lines over stdio。一行一个 JSON 文档，UTF-8，无内嵌换行；请求带 `id`，响应回同一 `id`；`stdout` 只放协议消息，`stderr` 只放日志；进程退出即 EOF。

不引入网络、发现机制、订阅模型、负载均衡。

---

## 4. 崩溃与未知

- 适配器进程死亡 → 所有 in-flight 动作产生 `unknown` 观测，**禁止**推断为失败或成功。
- 核心必须能区分 **"适配器说不知道"** 与 **"适配器死了"**。两者在账本里是不同的事实。
- 适配器无状态重启；会话内的临时状态不得跨重启假设存在。

---

## 5. 控制权租约

用户随时可以直接操作同一个被控实例。适配器申报 `exclusive`；持租约期间，用户操作必须显式让渡。`observe` 不得获取租约。

---

## 6. 禁令

| 不准进契约 | 因为 |
|---|---|
| 软件名、API 名、COM、窗口句柄、点击坐标 | 一进核心，O(1) 变 O(N) |
| 动作的具体实现方式 | 由适配器决定 |
| **verdict（一致/矛盾）** | 那是认定，不是观测 |
| 事件粒度 / 界面 / 传输拓扑 | 应用层的事 |
| 任何"真值"承诺 | 账本存声明 |

---

## 7. 一致性档（适配器）

| 编号 | 要求 |
|---|---|
| `A1` | `capability` 如实申报，`max_tier` 不高于实际能力 |
| `A2` | `act` 三态齐备，且不含"成功" |
| `A3` | 幂等重放不产生第二个副作用 |
| `A4` | `observe` 通道独立于 `act`，回报真实档位，不返回 verdict |
| `A5` | 仅 `C0` 观测不得导致冻结 |
| `A6` | 崩溃后 in-flight 归 `unknown` |

## 8. 设备端自报类观测的申报口径（`[DEV-SELF-2026-10-10]`，ZeroPage 补定）

> **背景**：每接一个新的被控系统（第四者），适配器作者都要回答同一个问题：
> 「**我这条「做到了」的证据，该怎么报？**」本节把口径固定下来，**不必每次从头讨论**。
> 依据：`kb/契约视角的两处封存-与乙轴定案的更正-2026-10-10.md`
> （其中记录了**两个被本契约当场纠正的设计错误**：把 `C0` 自校当认定依据、让适配器回 verdict）。

**定义**：设备端自报类观测 = **被控设备/工具自己产出的量**（芯片自算 CRC、烧录器窗口内自检回执、
软件自己导出的网表/DRC、回放统计）。对立面是"我方进程的复算"（那是另一路，见 8.3）。

### 8.1 三条硬口径（违反即不得支撑冻结）

1. **必须报 `tier`**：`C1`（新进程/新会话回读）/ `C2`（离线产物、第三方可离线复算）/ `C3`（跨机跨人）。
   **同一次动作内取得的比对（如烧录器的 `-v` 自校）属 `C0` ⇒ 不得支撑冻结** —— 它是「旁证」，不是「认定」。
2. **不返回 verdict**：`result` 只放**断言集**（标量键值）；`consistent` / `contradicted` 由核心按
   `SPEC.md` §4.1 判定（§1.3 与 §6 已定，此处重申为**设备端自报**场景的适用条款）。
3. **`evidence` 不得填「被观测对象自身的 id / 哈希」**（见本文件附录的 ⚠️）——
   否则同一对象的**两路独立观测会被合并**，`d_eff` 从 2 掉到 1，动作反而**无法被认定**。

### 8.2 一次动作要凑齐「能否定」的最少观测组（示例：把固件写进芯片）

| 观测 | 档位 | 为什么 | 它回答什么 |
|---|---|---|---|
| **设备自报**（芯片 CRC / `method=checksum` 回读）| **C1** | 新进程重开读回、外部世界自产 | 芯片里**现在**是什么 |
| **我方独立复算**（按 flash 布局从目标文件复算 CRC-32/MPEG-2）| **C2** | 离线产物、第三方可复算 | 「写入 == 读回」的另一路 |
| （动作回执内的自校，如烧录器 `-v`）| `C0` | 同一会话 | **旁证**：动作跑完了且被工具校过 |

**两路独立（C1 + C2）都指向同一 `expect` ⇒ 才谈得上认定**；只靠 `C0` 不得冻结。

### 8.3 何时"我方的复算"不算独立（防自欺，已发生过一次）

**引擎自己写的副本、再读回来** —— 换进程、算哈希都不改变"**同一份字节**"的事实
（2026-09-29 的 v0.1.121 假乙轴作废事故）。
判据只有一句：**这份量是不是外部世界（设备 / 软件）自产的？** 不是 ⇒ 不产轴。

## 附：运行时的请求 / 响应帧（**ZeroPage 补定**，2026-09-29）

契约原文只规定了「三个原语」，**没写线上帧长什么样**（这正是实现时最容易各写各的地方）。
ZeroPage 侧的运行时（`crates/adapter`）按**如下帧**实现 —— 写适配器照这个来即可。

- **传输**：`stdin`/`stdout`，**一行一个 JSON**（JSON Lines，UTF-8，`\n` 结尾）。
  **不得输出多行 JSON、不得在同一次响应里塞两个对象。**
- **请求**：`{"id": <整数>, "op": "capability" | "act" | "observe", ...}`
- **响应**：`{"id": <与请求相同>, "ok": true, "result": {...}}`
  或 `{"id": ..., "ok": false, "error": "<文本>"}`
- **每个请求必须恰好回一帧**（不许不回、不许回两帧）；`id` 必须原样带回。

### capability

请求：`{"id":1,"op":"capability"}`

响应 `result`：`{adapter, types[], channels:[{id,tier,read_only,desc}], max_tier, reversible, exclusive, idempotency}`

> 运行时**拒收高报**：任一 `channel.tier` 高于 `max_tier` ⇒ 判为不合格，**该适配器不装配**。

### act

请求：`{"id":2,"op":"act","type":"warrant://types/…@1","args":{…},"nonce":"…"}`

响应 `result`（**只有这三种**）：

| `status` | 含义 | 运行时随后做什么 |
|---|---|---|
| `accepted` | **已受理 —— 不是做成了** | **必然**发 `observe` |
| `rejected` | 明确拒绝（`reason` 必填） | 记为 REJECTED |
| `unknown` | 无从判断（模态框吞消息等） | **必然**发 `observe`，**禁止推断** |

### observe

请求：`{"id":3,"op":"observe","subject":"<claim id>","expect":{…},"channel":"<channel id>"}`

响应 `result`：`{method, result:{…}, observed_at:"<RFC3339>", tier:"C0..C3", evidence:["…"]}`

> `evidence` = 本次观测**所依据的上游证据 id 列表**（可为空 ⇒ 直接观测）。
> ⚠️ **不要把「被观测对象自身的 id / 哈希」填进来**：那会让同一对象的两路独立观测被判成
> 同一份证据而**合并**，`d_eff` 从 2 掉到 1，动作反而**无法被认定**（详见 `PROTOCOL.md` 的说明）。

### 异常一律 `unknown`

进程崩溃 / 30 秒无响应 / stdout 关闭 ⇒ 运行时**统一按 `unknown` 记**，
并在 reason 里写明「禁止推断」—— **绝不**推断为失败或成功（契约 §0 / §4）。
